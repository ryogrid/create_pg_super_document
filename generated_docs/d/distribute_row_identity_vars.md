# distribute_row_identity_vars

## Location
src/backend/optimizer/util/appendinfo.c: 965 - 1036

## Overview
Ensures that all target relations in an inherited UPDATE/DELETE/MERGE query will generate the necessary row identity columns, distributing ROWID_VAR references to relation target lists.

## Definition
void distribute_row_identity_vars(PlannerInfo *root)

## Detailed Description
This function is called after all row identity columns have been identified for an inherited UPDATE/DELETE/MERGE query to ensure that these columns will be properly generated by all target relations. It handles the distribution of row identity variables across the inheritance hierarchy, making sure that ROWID_VAR references are copied into the target relation's reltarget list.

The function serves a similar purpose to build_base_rel_tlists() but specifically handles ROWID_VAR Vars that would not be understood by the standard target list building process. It operates after inheritance relations are expanded and ensures that row identity variables are propagated to all necessary child relations.

The function includes special handling for edge cases where constraint exclusion might have suppressed all leaf relations, ensuring that the executor still has access to row identity columns even when no rows will be processed.

## Notes and Other Information
- Only operates on inherited UPDATE/DELETE/MERGE queries (returns early for non-inherited or non-DML operations)
- Handles an edge case where constraint exclusion eliminates all leaf relations by re-adding row identity columns from the parent relation
- Copies ROWID_VAR references from processed_tlist into the topmost target relation's reltarget list
- The actual distribution to individual leaf target relations occurs later during appendrel expansion in set_append_rel_size()
- Assertions verify that non-inherited operations should have no row identity variables
- The function ensures that the executor will have access to necessary row identification information even in complex inheritance scenarios
- Target list costs and widths are computed later in the planning process
- This function is a critical component for making inherited DML operations work correctly across partitioned tables and inheritance hierarchies
